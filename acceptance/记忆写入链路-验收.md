## 3. 真机账本核对（v2 新增）

读到的实际文件：`memory.jsonl` 5 条、`state.json`（`turns=5`、`stateWrites=5`）、`audit.jsonl` 227 行。

| 观察 | 证据 | 含义 |
|---|---|---|
| 5 轮全部写入成功，无一条被拒 | 5 条 `memory_write`，`rejected` 全为空 | 拒绝路径在本会话是冷代码，未被执行 |
| 5 条 entry 的 `source_trust` 全是 `user_explicit` | `mem_001`–`mem_005` | 恰好本轮都是用户原话；一旦工具分支生效（`'system'`），就会写出闭集外的值 |
| `sourceQuote` 都是当轮原话前缀 | 如 `mem_005` = 「你错了，别再敷衍」 | W3 只能证"非空 + 前缀"，证不了逐字 |
| `state.json` 的 `turns` 与条目数一致（5 vs 5） | `stateWrites=5` | 计数正确，但语义被标成"写请求"，且忽略 `rejected` |
| 5 轮 `matched` 恒为 0 | `pre_step` 审计 | 前 2 轮 `stage=cold` 抑制；后 3 轮线索不命中。**召回链路在本会话没有被真正检验**，不能据此说召回没问题 |
| **tool/result 事件多次出现，`origin=tool` 的写入 0 条** | 审计有 `tool/result`，无任何 tool 条目 | 见 W16 |

**W16（新发现）**：工具写入分支从未触发。`index.js:384-401` 依次从 `data.message.toolName` / `data.toolName` / `data.name` 取名字，取不到就整条跳过。真机里 `tool/result` 事件不少，却没有任何 tool 条目：按代码推，只能是三个取值位都没取到（该项校验必过，若取到名字就会落盘并记审计）。更糟的是该分支 `if (w.written)` 才写审计（`:395`），被拒绝时**静默无记录**——与 W11 同源。

**W17（判断，非事实）**：`(subject, relation)` 被当成事件流键用（`relation=goal_001`、`object=new/progress/obstruction`）。按 MEM-1.2 字面，这三条应互相取代；但从语义看它们是三件先后发生的事，不该取代。**要么键错了，要么写入粒度错了**，二者不可能都对。这条需要设计决策，不能只改代码。
