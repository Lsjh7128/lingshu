## 1. 审计口径与环境事实（先说清楚，避免误读）

### 1.1 H0 给的两个数字怎么对上

H0 提到"461 项 Python 断言 + 292 条插件断言"。本次实测：

| H0 数字 | 实测口径 | 对应关系 |
|---|---|---|
| 461 项 Python | **461 = 10 个"引擎/核心"测试文件的断言数**（控制 159 + pipeline 36 + pipeline_integration 65 + constitution 26 + agent_state 45 + gray 27 + learning 23 + onboarding 50 + proposal 18 + astrbot 12 = 461） | 项目还有 3 个标定/混沌文件（134 + 156 + 117 = 407），合计 **868** |
| 292 条插件 | **292 = v4.2 时点**的 106 host + 45 stress + 141 control；v5.1 已扩到 **188 + 45 + 148 = 381** | 所以 292 不是"现在只有 292"，而是旧版本快照 |

**结论**：H0 的两个数字都能在仓库里对上具体来源，不是虚报；但要评估"当前测试严密性"，基线应使用 **868（Python）+ 381（JS）**。

### 1.2 环境坑（影响复现，不影响断言语义）

本机 DSH `workspace-write` 沙箱下 `tempfile.mkdtemp()` 创建的目录不可写/不可删，导致 `test_chaos_calibrate.py` / `test_shadow_analysis.py` / `test_run_chaos.py` 直接运行会 `PermissionError`。审计使用 **`<REPO_ROOT>\.tmp\audit\run_py_with_shim.py`** 运行 Python 测试：它只替换临时目录的创建/清理，**不改任何断言、不改被测代码**。用 shim 后 13 文件 868 项与作者文档记录逐项一致。因此本报告覆盖率与变异结果在此环境下可复现；换一台不受该沙箱限制的机器应得到同样断言结果（这一点是环境适配，不是"改考卷"）。

### 1.3 覆盖率工具

本机没有 `pytest` / `coverage.py` / `c8`，pip/npm 安装不可靠。A5 用 Python 3.12 标准库 **`sys.monitoring`（PEP 669）** 自建 line+branch tracer；JS 用 Node 内置 **`NODE_V8_COVERAGE`**。方法、近似点、下限说明见 §5，原始数据可复算。

- 最大的结构性风险是 **`tools/` 26 个文件只有 3 个被执行**；这些工具生成报告/候选/回放集，出错会污染"参数标定"证据链。
- JS 的行覆盖高（95%），但 block 覆盖只有 56–75%，说明**错误分支/异常分支**覆盖明显弱于正常路径——与 §4 的"异常占比贴线"互相印证。
