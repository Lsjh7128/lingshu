## 2. 最重要的发现：DSH 的真实插件模型（直接改我们的架构假设）

这是本次调研**最有价值的一手材料**，来自两处：
`awesome-dsh-plugin/data/capabilities.json`（3841 条扫描结果）与
`agentmemory/docs/dsh.md`（一个已跑通的 DSH 原生插件）。

### 2.1 DSH 有"能力声明 + 红线扫描"机制 —— 这解决了我们的 P0-1（强制点）

`capabilities.json` 是 `dsh-trust-check@0.1.13` 对 3841 个插件的扫描结果，每条：

```json
{
  "version": "0.5.10",
  "spec": "github:00080000/dsh-project-memory",
  "capabilities": ["shell", "fs-write", "fs-read", "env", "llm"],
  "redLines": [],
  "scannedAt": "2026-09-24T17:02:46.730Z",
  "tool": "dsh-trust-check@0.1.13"
}
```

**能力词表（全集 10 种，按出现次数）**：

| 能力 | 插件数 | 含义 | LINGSHU 需要吗 |
|---|---|---|---|
| `fs-read` | 2880 | 读文件 | ✅（读 rules/、replay-set/） |
| `fs-write` | 2259 | 写文件 | ✅（状态、记忆库） |
| `env` | 2205 | 读环境变量 | ⚠️ 尽量不需要 |
| `network` | 2182 | 联网 | ❌ **不需要** |
| `shell` | 1634 | 执行命令 | ❌ **不需要** |
| `credentials` | 454 | 读凭证/密钥 | ❌ **绝对不需要** |
| `llm` | 347 | 调用模型 | ✅ |
| `dynamic-code` | 347 | 运行时代码执行 | ❌ 不需要 |
| `host-runtime` | 296 | 访问宿主运行时 | ⚠️ 需评估 |
| `subagent` | 86 | 派生子 Agent | ❌ 不需要 |

**红线（`redLines`）里最常见的一条**：

> `reads credentials/secrets AND has network access` —— **353 个插件命中**

**对我们的直接结论**：
1. 我们的"不可修改/不可关闭"**可以表达为能力约束**，而且宿主**已经能扫**：
   LINGSHU 只需 `fs-read` + `fs-write` + `llm`，**不申请** `network` / `shell` / `credentials` /
   `dynamic-code` → 天然没有"偷改配置后外传"的路径。
2. 双向强化：`_frozen/` 只读挂载（我们自己） + 能力最小化（宿主扫描） = 两层。
   **这比我们原来"只靠提示词/只靠只读挂载"的单一手段强得多。**
3. 应该新增一份 `capabilities.yaml`，把"我们需要哪些能力、为什么不需要其余"写死，
   并进 `frozen-manifest`。

### 2.2 DSH 的钩子点：我们猜的三个，基本对得上

`agentmemory/plugin/hooks.json` 用的是这套（Claude Code 风格，其 DSH 原生插件提供等价能力）：

| 钩子 | 时机 | 我们在哪用了它 |
|---|---|---|
| `SessionStart` | 会话开始 | 冷启动阶段判定、加载记忆 |
| `UserPromptSubmit` | 用户消息提交后、模型调用前 | **≈ 我们的 `agent/pre-step`**：检索 + 编码 |
| `PreToolUse` / `PostToolUse` | 工具调用前后 | 工具结果入记忆、关系/目标更新 |
| `Stop` | 本轮结束 | **≈ 我们的 `turn/end`**：情感/目标/关系更新落库 |
| `SessionEnd` | 会话结束 | 巩固触发、Hot 清空 |

并且 `agentmemory/docs/dsh.md` 明确写了关键一句：

> **"supplies saved context as reference data before the first model request"**

——即"模型第一次请求之前注入参考上下文"，这正是我们"每轮检索注入"的实现位置。

### 2.3 插件注册与注入通道（对我们 H1/H5 的答案）

同一个文档给出了 DSH 侧的具体机制：

| 机制 | 路径/形态 | 对我们意味着 |
|---|---|---|
| 插件注册 | `$DSH_HOME/cordis.patch.yml`（家目录级，跨 profile 共享） | 我们的"宿主核心"就是它；`DSH_HOME` 默认 `~/.dsh` |
| 记忆工具指引 | `$DSH_HOME/AGENTS.md`（首次请求时加载） | **这就是我们"常驻原则"的落点之一**，不必强依赖 `systemPrompt.section()` |
| 原生插件 | 一个 `dist/integrations/dsh.mjs` 即可，无需单独插件包 | 我们的"插件套件"可以是**一个包里的多个模块**，不必拆 N 个包 |
| 凭据 | 通过 `!!js` 配置语法在启动时求值，不写进 patch 文件 | 我们的"密钥不落盘"要求可以照这个做 |
| 失败缓冲 | 有界本地 spool + 重试（宿主在跑/下次启动时） | 我们 `docs/14 §2.3` 的"本地缓冲 + 补写"是对的，可直接照此实现 |

**结论**：H1（注入点）✅ 存在，但有两条通道（AGENTS.md + 原生插件注入），
**不要只押 `systemPrompt.section()`**。H5（持久化）✅ 存在（文件级 KV）。
H2/H3（钩子）✅ 等价物存在，**具体命名必须以 DSH 文档为准**（本次未直接读 DSH 官方文档）。

## 3. 值得抄的七项（每项标注落点）

### ① 预算化召回契约（最有价值）→ `docs/02 §6` + 新增 `contracts/recall.schema.json`

**问题**：我们现在只说 `topK=3`、`token ≤15%`，但**没定义"预算装不下时怎么办"**。
这是真实高频场景（一条 Cold 摘要 + 一条长 episodic 就超了）。

**agentmemory 的做法**（`docs/recall.md`）：

| 字段 | 作用 |
|---|---|
| `matched_count` | 命中数（限于请求范围，不是全库） |
| `content_truncated` | 该条被截短，**ID 保留** |
| `excluded_by_budget` | 因预算未返回的命中数 |
| `excluded_results` | **最多 10 条恢复引用**（ID + 会话 ID + 短标题） |
| `minimum_budget` | 连第一条最小预览都装不下时返回 |
| `truncated` | 内容截短或结果省略 |
| `tokens_used` | 启发式：序列化长度 / 3，向上取整 |

三条规则特别值得抄：
1. **保序装填**：始终先放排名最高的那条，必要时给它降级为预览；
   **不允许用"更短的低排名条目"替换掉长的高排名条目**；
2. **截短不丢 ID**：被截短的结果仍然可展开（expand by ID），完整内容在库里不变；
3. **诚实标记**：`minimum_budget` 明确告诉调用方"预算不够，请加钱或展开引用"，而不是静默返回空。

**怎么改**：我们的召回模板加 `excluded`/`truncated` 元数据；**元认知据此把
`confidence_level` 降到 `mid` 并给 `hedge`**（"我记忆里还有几条，但这次没带出来"）。
这条同时也补上了我们 `docs/02` 的一个空洞：**"没注入"≠"没有记录"**。

### ② 层过滤先于候选截断 → `docs/02 §6.1`

原文一句：

> The layer filter runs before keyword and vector candidate limits and graph ranking,
> so a large observation history cannot consume the saved-memory candidate slots.

翻译成我们的问题：**Cold 有几十万条时，会不会吃掉 Warm 的 `topK=3` 名额？**
我们的检索流程写的是"线索匹配 → 种子 → 扩散 → 合并 → 排序 → top3"，
**没有规定按层过滤在截断之前**。必须补一条：

> `layer_filter` 必须在候选截断与扩散之前执行；Cold 命中不得挤占 Warm 候选位。

### ③ 遗忘要能"先演练" → `docs/02 §3.3` 巩固器

`src/functions/auto-forget.ts` 的做法，四条都可抄：

| 做法 | 我们的差距 |
|---|---|
| `dryRun: true` 参数，先出清单不删 | **我们完全没有**。遗忘是高风险动作，应该默认 dry-run |
| 每条记忆可有 `forgetAfter`（显式 TTL） | 我们只有衰减函数，没有"记住 7 天" |
| 硬删条件明确：`age > 180 天 且 importance ≤ 2` | 我们只归档不删，没有"真删"条件 |
| 删除要同步 6 处：KV、facet、访问日志、搜索索引、向量索引、图片引用计数 | 我们只写"物理删除 + revisions"，**没有同步清单** |
| 删除前 `withKeyedLock` + **重新读取再判条件** | 我们没写并发安全的二次校验 |
| 每次删除写 audit（`reason` + `timestamp`） | 我们有审计思路，但没落到"删除必须带 reason" |

**怎么改**：`docs/02` 的巩固器加"两段式"——**先 dry-run 出清单 → 人工/指标确认 → 再执行**；
并把"删除六步同步清单"写成硬要求（我们的 `docs/15` 也该加一条验收：删一条，六处都干净）。

### ④ 巩固的"频率门槛"与 XML 输出 → `docs/02 §3.3`

`src/prompts/consolidation.ts` 的提示词只有 15 行，但每条都是硬约束：

```
- Extract only facts that appear in 2+ episodes or are highly confident
- Confidence reflects how well-supported the fact is across episodes
- Combine overlapping information into single concise facts
- Skip ephemeral details (specific error messages, temporary states)
```

**我们缺的是第一条**：我们只按 `importance` 区间决定提取，**没有"出现 ≥2 次"这个频率门槛**。
这条能直接降低"一次性细节被固化成长期记忆"的风险，也天然解决了"去重"的一半工作。

另外他们用 XML（`<facts><fact confidence="...">`）而不是 JSON —— 好处是不会因为
一个引号解析失败整批丢掉。**我们 `docs/02` 是纯 JSON 数组**，可考虑关键路径留一个 XML 兜底。

### ⑤ 契约要"生成 + 摘要 + 漂移测试" → 缓解我们的 R2（契约漂移）

`engram/docs/AGENT-CONTRACT.md` 把契约工程化做到了教科书级：

- 契约文件**由代码生成**（`go generate`），不手写；
- 有 `-check` 模式：**契约与代码不一致就退出码 1**（这就是"漂移测试"）；
- 契约带 `revision`（语义版本，非 SemVer）+ `digest`（整份文档的 SHA-256）；
- **canonical 编码规则写死**（键排序、数字保留原始 token、字符串转义规则），
  并明确"`1e+02`、`100`、`100.0` 是等价值但不同 digest 输入"；
- 提供**跨语言测试向量**（Go + Node 各自复现同一 digest）；
- 最值得学的一句：状态字段自我限定 —— `status: "mcp-foundation"`，
  **"这不是 Pi 已实现同一契约的声明"**。

**怎么改**：
1. 我们的 `contracts/*.schema.json` 也应"由代码/规则生成 + `-check` 漂移测试"，
   而不是手写；`frozen-manifest.yaml` 的哈希校验只是"防篡改"，**不防"代码与契约不一致"**；
2. 每个契约加 `status` 字段，**只写事实**（如 `status: "designed-not-implemented"`）；
3. 把"digest + canonical 规则"补进 `frozen-manifest`（现在只写"sha256 of file"，没定义
   规范化方式，换个编辑器换行就误报）。

### ⑥ 能力最小化声明 → 新增 `capabilities.yaml`

见 §2.1。写法建议：

```yaml
plugin: lingshu
capabilities:
  required: [fs-read, fs-write, llm]
  notRequested: [network, shell, credentials, dynamic-code, subagent, env]
  rationale:
    network: "记忆与人格不需要外网；引用核验由人工完成"
    shell: "不执行任何外部命令"
    credentials: "不接触任何密钥"
    env: "不读环境变量，配置全部来自 rules/"
```

**这条能直接写进 README 的安全立场**：`3841 个 DSH 插件里 353 个踩了
"读凭证 + 联网"红线；LINGSHU 两者都不申请。`

### ⑦ 钩子命名对齐宿主 → `docs/14 §2.2` + `assumptions/未验证.md`

把我们的 `agent/pre-step`、`turn/end` 改名为宿主实际存在的 `UserPromptSubmit`、`Stop`
（或 DSH 官方命名），并在事件契约里加一行映射表。**命名不对齐是集成期最容易被卡住的地方。**

## 4. 明确**不**抄的

| 项 | 为什么 |
|---|---|
| `agentmemory/DESIGN.md` | 打开发现是**兰博基尼官网的 UI 设计系统**，与记忆架构无关。教训：文件名要能被检索到正确的东西——我们 `docs/NN-主题.md` 的编号式命名坚持住 |
| 他们的扁平 `memories` 列表 | 我们 Hot/Warm/Cold + 衰减 + 取代更细；他们的强项是"捕获"不是"分层" |
| 用 `Jaccard > 0.9` 判"矛盾"并标 `isLatest=false` | 他们**不区分"取代"与"重复"**，一个阈值管两种语义；我们用 `(subject, relation)` 单键 + 去重分离，更精确。**但可借鉴"用字面重叠而非语义相似"这一点**——我们的 `MEM-0.1 禁语义相似度`其实与它同源，可以把 `dedupe` 的相似度实现也改为字面 Jaccard（便宜、可解释、不违反原则） |
| 直接物理删除 observation | 我们的不变量要求"可回滚"；可以删，但必须 dry-run + audit + 可恢复窗口（如 7 天软删除区） |
| 可选的 CrossEncoder 重排 | 思路可取（`docs/reranking.md` 的"全有或全无"降级非常好），但它是 20MB 级本地模型，违背我们"零额外依赖"的部署姿态。列为 v3.1 观察项 |

**特别值得记住的一条设计智慧**（来自 reranking 文档）：

> 任一候选推理失败或返回非法分数 → **整个请求保持原始排序**，不混合两种排序。

即"**要么全用模型分，要么全不用**"。我们将来任何引入模型打分的改动都该照这条：
**不要出现"一半条目按模型分、一半按规则分"的混合排序**，那会让归因彻底失效。
