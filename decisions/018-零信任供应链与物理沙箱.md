## 1. 背景与威胁

### 1.1 为什么现在需要（宿主不提供强制点）

DSH 的插件是普通 JS 模块：宿主 `loader` 应用 `cordis.patch.yml` 后**直接加载并执行**，`import` 期就会跑插件顶层代码。本项目已核实（`docs/00 §4.1`）：

- **H4 证伪**：不存在"只读挂载 / config 校验"——patch 层可以整段覆盖任何插件 config。**宿主的现状是"加载即信任"。**
- **H1/H3 证实**：`systemPrompt.section`、`agent/pre-step` 等钩子可以被任意插件注册，且注册即生效。

结论与 `ADR-013` 同构：**没有任何宿主级机制能替我们校验第三方插件**，强制点只能放在"我们自己控制的加载路径"上——即"经 S-CAP 加载器加载的插件"。

### 1.2 威胁模型（两类，缺一不可）

| # | 威胁 | 形态 | 归属 |
|---|---|---|---|
| T1 | **第三方插件供应链投毒** | 恶意/被劫持的认知插件在 import 期或调用期：越权读写、偷偷联网外传、读凭证/环境变量、加载原生 addon、派生子 Agent；或 Manifest 声明与实际代码不一致 | **本 ADR（基础设施层）** |
| T2 | **大模型越权工具调用** | 模型被诱导或上下文污染后产出危险 `tool_use`（删文件/外发/执行/读凭证） | `docs/24`（T-UCA 判定）+ `ADR-017`（可解释权限请求 / degrade 的可解释转述） |

**本 ADR 只解决 T1。** T2 已有认知控制面：`docs/24` 的 16 条 T-UCA 判定 + `ADR-017` 的 `degrade` / 可解释提权请求（事实层六项 + 风格层受约束）。两层的衔接是硬约定：

1. T1 判 `deny` 的插件**不注册任何钩子** ⇒ 它不会产生任何工具调用，T2 的判定与表达机制对它是空集；
2. T1 判 `allow_sandboxed` 只说明"代码只拿到申报能力" ⇒ 它产出的工具调用**仍然**要过 T-UCA 与 `ADR-017`；
3. 两层都只能约束"经本路径"的对象，**都不声称全系统强制**（与 `ADR-013 §4.4` 同口径）。

### 1.3 本项目自身的能力承诺（为什么可以这么严）

`rules/capabilities.yaml`（v3.0.1，改动需 ADR）：LINGSHU 只申请 `fs-read` / `fs-write` / `llm`；`network` / `shell` / `credentials` / `dynamic-code` / `subagent` / `env` 写死为 `notRequested`；`host-runtime` 为条件能力（`requested: false`）。词表共 **10 种**，来源是 DSH 生态已有的 `dsh-trust-check` 能力扫描（`awesome-dsh-plugin/data/capabilities.json`，覆盖 **3841** 个插件）。S-CAP 直接复用这套词表，**不新造词**——第三方插件与 LINGSHU 自身用同一把尺子。

### 1.4 诚实声明（先写，防止日后误读）

- 本轮**没有发生任何真实供应链投毒事件**，本 ADR **不引用**具体事件；威胁模型按"宿主不校验 + 插件 import 即执行"的机制推演，攻击样本全部是**合成用例**。
- 本轮**没有真实第三方插件生态**：所有断言都是在临时目录里构造的良性/恶意插件。
- 因此本 ADR 只能声称"**机制可达 + 物理边界可复现**"，**不能**声称"提高了真实供应链安全水平"。

## 2. 决策（五条）

### D1 · fail-closed 默认拒绝：deny = 不加载 / 不注册 / 审计 / 挂起

任何一层校验不通过即 `deny`，且 deny 必须同时做到四件事（`docs/26 §2.2`）：不 `import` 入口、不 `spawn` 子进程、不注册任何钩子（段落/pre-step/工具/状态）、写 `supply_chain*` 审计 + 中文告警 + `SANDBOX_STATE.suspended=true`（后续插件不再尝试加载）。宿主侧任何异常（读盘/spawn/协议）一律折算 `deny`，**不存在"带异常继续加载"**。

`verdict` 只有两个值：`allow_sandboxed`（只许在沙箱里跑）与 `deny`；**没有"部分放行"**。

### D2 · 独立子进程 + Node permission model（而不是 WASM / worker_threads）

`spawn` 一个**独立 node 进程**，参数由 `buildNodeFlags()` 从申报能力推导：

- 恒给：`--permission --no-warnings --no-addons --disable-proto=throw --disallow-code-generation-from-strings --max-old-space-size=128 --allow-fs-read=<pluginDir>`（+ 宿主追加 `--allow-fs-read=<sandbox-child.mjs>`）；
- `fs-read` → 追加 `--allow-fs-read=<每个声明作用域>`；`fs-write` → **仅授予时**追加 `--allow-fs-write=<每个声明作用域>`；`shell`/`subagent` 不传 `--allow-child-process`/`--allow-worker`（即拒绝）；
- 子进程只把 `manifest.exports` 暴露成 RPC 方法；父进程用 **127.0.0.1 TCP + newline-delimited JSON + 一次性 token + pid 绑定**通信（stdio 管道在 DSH 沙箱内 EPERM，本机实测）。

实测（Node v24.21.0）：越界写/读/`mkdir` → `ERR_ACCESS_DENIED`；`execSync` / `new Worker` / `process.binding` → `ERR_ACCESS_DENIED`；`eval`/`new Function` → `EvalError`；`__proto__` 赋值 → `Error`（详见 `docs/26 §6.5`）。

### D3 · 策略外置、单一来源、deny-all 兜底

规则表（10 能力词表、10 条扫描规则、11 项 precedence、错误码、沙箱参数）**只**存在于 `contracts/supply-chain-policy.json`；JS/Python 实现都**运行时读同一文件**，不内联冻结副本（内联副本与契约漂移 = 安全漏洞）。发布态允许插件目录内的副本（候选 3）或 `LINGSHU_SUPPLY_CHAIN_POLICY` 覆盖（候选 1）。全部候选失败 → `FALLBACK_POLICY`：**known=[]、rules=[]、`verdicts.clean="deny"`、env_allowlist=[]**，即"没有策略就什么都不加载"。

策略文件本身也过零信任：形状不对（缺 `policy_version`/`capabilities.known`/`scan.rules`/`decision.verdicts`）就**跳过该候选**，不"尽力使用"。

### D4 · 能力词表复用 DSH `dsh-trust-check` 的 10 种

`fs-read` / `fs-write` / `llm` / `network` / `shell` / `credentials` / `dynamic-code` / `subagent` / `env` / `host-runtime`，与 `rules/capabilities.yaml`、`contracts/agent-contract-v1.json` 完全一致；**不新增词、不改语义**。理由：与生态工具（`dsh-trust-check` 的 redLines 扫描）同口径，插件作者写一次声明、两边都能读；也避免"LINGSHU 自己发明一套豁免词"。

### D5 · 七种能力永不可授予（`never_grantable`）

`network` / `shell` / `credentials` / `dynamic-code` / `subagent` / `env` / `host-runtime` 一旦出现在 Manifest 即 `forbidden_capability`（`SC-E10`），在 spawn 之前拒绝；**不存在"先放进来再降权"的路径**。可授予的只有 `fs-read` / `fs-write` / `llm` 三种，其中前两种必须带作用域且只能授予到子目录。

`network` 永不可授予的直接理由是物理事实：**Node permission model 不覆盖网络**（实测 `net.listen/connect` 在 `--permission` 下正常）——给它开一个 OS 层拦不住的权限，等于放弃边界。

## 3. 被否方案与原因

| 方案 | 为什么否 |
|---|---|
| **WASM 沙箱**（wasmtime/wasm-bindgen 类） | 无法运行现有 ESM 插件生态：插件需要 `node:fs`、宿主 RPC、`llm` 调用；WASM 只隔离纯计算，不解决原生 addon、子进程、宿主管道风险。迁移成本 = 重写全部插件 + 新建宿主 ABI。**降级为后续方向**（见 §6）。 |
| **`worker_threads` 隔离** | worker 与主线程**共享同一进程的权限与内存**，无法给 worker 单独的 permission 集；恶意插件可以在主进程内存里翻凭证，且无法可靠 kill（共享事件循环）。 |
| **纯静态扫描（不建沙箱）** | 词法级检查可被拼接/模板/正则误剥绕过（`docs/26 §4.3` 已实测三条漏报）；把安全押在"正则永远不漏"上不成立。扫描保留为**前置拒绝**手段，不是最终防线。 |
| **纯依赖宿主沙箱**（等 DSH 提供插件隔离） | `docs/00 §4.1 H4` 已证伪：宿主现在没有 config 只读、没有能力校验；"等宿主"= 无限期无边界。本项目只能在可接入点上自己建强制点。 |
| **stdio 管道 JSONL RPC** | 被环境证伪：DSH 文件沙箱禁止打开命名管道，`spawn(..., stdio:'pipe')` 在本机 **EPERM**（`stdio:'inherit'` 正常）。改为 TCP loopback + token 是**约束下的选择**，不是设计偏好。 |
| **内联冻结一份策略到 JS** | 内联副本会与契约文件漂移，而策略漂移在本模块就是安全漏洞。改为运行时读文件 + 文档 §7 内嵌 JSON 的**机器校验**（`tests/test_supply_chain.py` 逐字段比对）来防漂移，而不是复制两份。 |
| **签名 / 依赖完整性校验**（本轮不做） | 需要 PKI、密钥管理、发布流程改造；当前仓库没有签名基础设施。本轮只做到"manifest 哈希 + 入口哈希"两级钉住，**防替换不防恶意包自带哈希**。列入解冻条件。 |

## 4. 后果与代价

**收益（机制层）**：

1. 未申报的底层 API 在加载前被拒（`SC-E11`），申报了不可授予能力在 spawn 前被拒（`SC-E10`）；
2. 即使扫描漏报，申报能力之外的 fs/exec/worker/addon/eval 副作用在 OS 层被拒（`ERR_ACCESS_DENIED` / `EvalError`）；
3. 插件崩溃/超时/握手失败都折算为 deny + kill + 挂起，不留半可用状态；
4. 策略单源 + 文档同帧 + py↔js parity，规则改动不会出现"只有一处生效"。

**代价（必须写进 README/论文）**：

| 代价 | 量级/说明 |
|---|---|
| 启动一次 node 探针 | `detectSandboxSupport()`：`spawn(node, ['--permission','-e','process.exit(0)'])`，超时 3000ms；不支持 → 全部 `SC-E01` deny |
| 每插件一次 spawn | 独立 node 进程（冷启动）；`ready_timeout_ms=5000` 上限；`call_timeout_ms=2000`；无预热池 |
| 插件作者负担 | 必须写 `plugin.manifest.json`（id/version/entry/exports/capabilities/fs 作用域/入口 sha256）；改代码必须同步哈希 |
| 误杀面 | 声明不全的良性插件会被 `SC-E11` 拒绝；`info` 级命中（SC-02/SC-09）同样 deny；severity **不分档**（`docs/26 §4.4`） |
| 漏报仍需沙箱兜底 | 扫描漏报（拼接/模板/正则误剥）不导致越权，但**兜不住网络与凭证外传**（网络无 OS 强制） |
| 可用性代价 | 一次 deny 后加载器挂起，需重启插件/进程恢复；子进程异常退出 = 该插件永久不可用（本次进程内） |
| 性能未标定 | 没有吞吐/延迟数据；`spawn` 开销与 RPC 往返均未 benchmark（`provenance: guess`） |
| 默认开启的风险 | `index.js` 默认 `supplyChain.enabled=true`，但 `plugins=[]` ⇒ 零开销；配置了插件目录才动作（§7） |

## 6. 解冻 / 扩展条件

1. **签名 / PKI**：出现可信发布通道（包签名、作者密钥、透明日志）后，才可能把"安装者提供的哈希"升级为"来源可信"；在此之前不得声称"供应链可信"，只能说"装完之后不可被悄悄替换"。
2. **网络强制**：出现 OS 级 egress 控制（防火墙/宿主代理/容器网络策略）后，`network` 才可能从 `never_grantable` 降级为"可授予但需显式审批"；当前任何"授予网络"的方案都不予考虑（Node permission model 无网络开关，实测）。
3. **WASM 运行时**：若插件生态不再需要直接触摸 Node fs/宿主 RPC（或出现稳定的 WASM 宿主 ABI），可以并行提供 WASM 沙箱作为**更细粒度**的可选项；WASM 不替代进程沙箱，二者是叠加关系。
4. **真实生态与样本**：接入真实第三方插件、采集真实恶意/可疑样本后，才能标定**检出率/误杀率/性能**；届时需要更新 `provenance` 与论文 limitations。
5. **发布态闭环**：插件目录内策略副本 + 打包一致性校验（`docs/26 §8.1`）落盘后，发布态才不是"默认 deny-all"。

## 7. 回滚方式

| 级别 | 操作 | 效果 |
|---|---|---|
| 配置级（最快） | `supplyChain.enabled = false` | 加载器不被调用：不探测、不 spawn、不写 `supply_chain*` 审计（`index.js` 懒加载，不 import `sandbox-host.mjs`） |
| 配置级 2 | `supplyChain.plugins = []` | 零开销空转，保留再开能力 |
| 接线级 | 回滚 `index.js` 的接线 hunk（`getSupplyChainRuntime` / `bootstrapSupplyChain` / status 行 / `ctx.effect` 卸载清理） | 加载器不再被引用；其余文件可留 |
| 策略级 | 删除/回退策略文件或环境变量 | 回落 `FALLBACK_POLICY` = **deny-all**（全部插件不加载）——这是兜底，不是回滚选项 |
| 代码级 | 删除 `supply-chain.js` / `sandbox-host.mjs` / `sandbox-child.mjs` / `supply-chain-sim.mjs` / `supply-chain-integration.mjs` / `engine/supply_chain.py` / `tests/test_supply_chain.py` / `docs/26` / 本 ADR，回滚 `index.js` 接线 | 回到引入前；重跑既有套件应无新增失败 |

**回滚红线**：不允许"把 `verdicts.clean` 改成 allow 但保留 deny-all 兜底代码"这类半回滚——要么用真实策略，要么彻底关掉加载器；`FALLBACK_POLICY` 的 deny-all 语义必须在任何回滚形态下保持成立（`tests/test_supply_chain.py` 有断言）。
