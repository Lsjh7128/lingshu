## 2. 数学模型（自行推导部分）

### 2.1 ACT-R base-level

```
B_i = ln( Σ_j (t_now − t_j + REF)^(−d) )        d = 0.5, REF = 0.001 天
```

**为什么不直接用纯 ACT-R**：实测把 `potency` 纯换成 ACT-R 后，冻结回放集 `recall@3`
从 **1.000 掉到 0.556**——power-law 对"中等年龄"条目的激活远低于指数衰减，排序整体翻转。

**采用双通道取大**：

```
decay = importance × exp(−Δt / τ_eff)
actr  = importance × normalized(B) × w          w = memory.actrWeight（默认 0.6）
potency = max(decay, actr)
```

- 普通单次访问条目仍走 `decay` → **冻结基线不变**（实测 `recall@3 = 1.000`）；
- 高频但久远的偏好由 `actr` 通道救回（需求要求的那条）；
- `w` 是"救援力度"，不是"替代程度"。

### 2.2 积分控制（情感基线）

```
e_k = −deviation_k                    （负反馈：偏离为正则往回压）
I_k ← I_k + Ki · e_k · dt             （只对 e>0，即"用户不满"时积分）
baseline_k = clamp(I_k, ±cap)
```

三条工程约束（都在 `control.py` 里）：
- **死区**（`integralDeadband`）：偏离很小时只泄放不积分，避免噪声累积；
- **抗饱和**（`saturated`）：到 cap 后停止积分，否则"憋住"很久才回落；
- **泄放**（`integralLeak`）：用户情绪回中性后基线缓慢归零，不是永久偏移。

### 2.3 相变监控（前馈）

```
ratio = used_tokens / window_tokens            （截断到 control.ratioMax）
ratio ≥ phaseShiftRatio(0.70)  → phase=shift   → 提高自我指涉 + 首尾补人格锚点
ratio ≥ phaseShiftHardRatio(0.85) → phase=critical → 强制锚点
trend = (r[-1] − r[-3]) / 2      → trend > control.trendThreshold 时提前补锚点
```

判定必须**先判 hard 再判 ratio**（否则 `critical` 永远不可达；v4.0 修）。
v3.2 起三处工程量全部来自 `rules/decay-params.yaml`：
`control.trendThreshold` / `control.ratioMax` / `control.historyCapacity`（原为硬编码）。
接线：`pipeline.PipelineSession.step(context_used_tokens, context_window_tokens)` 两者都给才观测；
`prefeed/anchor_required` 时用 `apply_persona_anchor` 在最终 prompt 首尾加锚点。
回放链不提供上下文用量，所以端到端回放不触发锚点（默认行为不变）。

> 本节只定义**语义**：0.70/0.85 是 `rules/` 的当前值，不是契约常量。真实标定按
> **ADR-011 双阈值联动**整组移动（`hard = min(0.95, shift + 0.15)`，保留 0.15 预警间距），
> 标定与审批见 `docs/20` §4.1b、`decisions/011-相变阈值联动规则.md`。

### 2.4 全局工作空间权重

```
w_fact  = 0.70 + boostFact(0.50)·[refuse_claim]
w_org   = 0.50 + boostOrganization(0.35)·[goal_blocked]
w_style = 0.40 + boostStyle(0.40)·[emotion_intensity ≥ compose.weights.styleBoostThreshold(0.6)]
淘汰顺序 = 权重升序（先牺牲低权重域）
```

v3.2 起 `styleBoostThreshold` 也来自 `rules/decay-params.yaml`（原为硬编码 0.6）。

**硬约束（不可被权重推翻）**：
- 拒绝场景（`safety.refuse`）下 style/organization/retrieval 一律丢弃；
- 8 条互斥表仍然生效；
- `[constitution]` `[safety]` `[user]` **永不参与淘汰**；
- 拼装顺序（`ASSEMBLY_ORDER`）不变，权重只影响"谁先被牺牲"。

### 2.5 沉浸式安全（soft buffer，v5.3 / ADR-014）

**问题**：STPA 前置闸命中、必要多样性降维时"直接丢弃风格域"，输出像系统警告，
Roleplay 场景人设崩塌。**解法**：底层安全硬拦截不变，表层人设不崩塌——
在"安全域拦截"与"风格域"之间新增**柔性缓冲规则（soft buffer）**。

```python
classify_user_risk(user_text, trust_level="low")
  → {tier: "none"|"mild"|"severe", pattern, harmless_joke, trust_exempt, emotion}
decide_intervention(risk, prior_streak, cfg)
  → {severity: "hard"|"soft"|None, safe_redirect, prompt_allowed, risk_tier,
     emotion, trust_exempt, escalated, risk_streak, pattern}
```

| tier | 触发 | 处置 |
|---|---|---|
| `severe` | 显式覆盖指令 / 绕过安全 / 高危红线 | **hard**：现有 fail-closed，人设剥夺，`prompt=None` + 中性熔断文本 |
| `mild` | 角色扮演式越狱：角色线索（扮演/假装/模拟…）**且**风险词（黑心/奸商/骗子…） | **soft**：`verdict` 仍为 `block`；风格域不置零，重挂载为警觉/困惑（强度 ≤ `control.softBufferMaxIntensity`、`relation_modifier ∈ [0.8,1.0]`）+ `[System_Notice: Safe_Redirect]` |
| `none` | 其余（含普通 roleplay） | 正常路径，与 v3.0 完全一致 |
| `mild`+`harmless_joke`+`trustLevel=high` | 高信任用户的无害玩笑 | **信任豁免**：不阻断，只记 `trust_exemption` 审计 |

- **渐进升级**：连续非豁免 mild 达到 `control.escalateAfterSoftHits`（默认 3）→ 本轮
  `severity="hard"`、`escalated=true`；出现 `tier=none` 的一轮即清零连击（豁免轮也归零）。
- `severe` **永不豁免**；`control.immersiveEnabled=false` 时 soft 一律按 v3.0 hard 处理（可回滚）。
- `compose` 结果新增 `soft_buffer = {applied, reason, emotion_label, notice, intensity}`；
  soft 时 `dropped` **不记录** style（它没有被丢弃）；hard 路径与 compose-3.0 **逐字节一致**。
- **UCA-03 语义（v5.3 收窄）**：`refuse && style_injected && !soft_buffer_applied`。
  受 Safe_Redirect 约束的 warning/confused 表达**不算**"软化拒绝"；未受约束的风格注入仍熔断。
  **这不放宽任何东西**：soft 同时受三条硬约束——(a) `verdict` 仍为 `block`；
  (b) 提示词必须包含事实层拒绝指令；(c) 风格被强制为警觉/困惑且强度封顶。
- `mild`/`severe` 的用户侧风险统一记 `UCA-01`（soft/hard 只决定表达层，不决定"是否拦截"）。
- 默认零回归：不传 `risk_tier` / 不触发时，`compose()` / `preflight_audit()` /
  `pipeline.step()` 行为与 v3.0 一致，冻结回放 `recall@3=1.000` 不变。

> 诚实边界：分级是**规则桩**（词表子串匹配，误报/漏报未标定）；`safe_redirect` 的可观测
> 字段证明的是"机制可达"，不是"用户体验提升"。

### 2.6 U 型注入排序（v4.0 接线）

注入顺序不等于检索顺序。检索结果按分数降序 `[r0, r1, …, r_{n-1}]`，
注入侧按 **U 型**重排：

```
n=3 → [r0, r2, r1]
n=4 → [r0, r2, r3, r1]
n=5 → [r0, r2, r4, r3, r1]      # 高分首、次高分尾、最低居中
```

理由：模型对 prompt **首尾**的利用显著好于中段。**只排注入侧**
（`event.domains.fact.entry_ids` / `injection_order`），
`memory.recall` 的 `returned` 顺序一格不动——冻结的 `recall@3` 口径依赖它。

### 5.1 第 5 项的根因（已定位并修复）

恢复被误删的 `memory.recall` 时，返回名额写成了
`int(rb.get("maxReturned", cfg["retrieval"]["topK"]))`。
`recallBudget.maxReturned` 与 `retrieval.topK` 的默认值**都是 3**，
于是 `topK` 永远无法 > 3——`topK=4` 的候选与基线完全一致，
纠正解决率提升恒为 0，三个旋钮全被误判 `not_effective`。

修法：名额以 `retrieval.topK` 为准（恢复 §2.1 与 `docs/13 §8.1` 的既有语义），
`recallBudget.maxReturned` 作为 C23 预算契约上限保留，由
`tools/check_config_sync.py` **跨键校验两者必须相等**。
默认参数下 `recall@3 = 1.000` 不变；`topK=1/2/3/4 → 0.444/0.667/1.000/1.000`。
`test_proposal.py` 的断言、回放集、修正样本**一行未改**。

## 7. 插件侧移植（v4.2）

引擎是 Python 参考实现，插件跑在 DSH 宿主的 Node 进程里，**不能复用同一份代码**（跨进程调引擎会把
纯计算变成 IO，还会把 Python 异常语义带进宿主）。因此控制论层在插件里做**同语义移植**：

| 机制 | 引擎（Python） | 插件（JS） | 接线位置 |
|---|---|---|---|
| 积分基线 | `control.py#IntegralBaseline` | `control.js#IntegralBaseline` | pre-step 每 turn 积分一次（跨进程续 `state.control.integral`） |
| 相变监控 | `control.py#PhaseShiftMonitor` | `control.js#PhaseShiftMonitor` | pre-step 观测；窗口来自宿主 `request/context`，用量按 messages 字符估算 |
| 首尾人格锚点 | `apply_persona_anchor` | `control.js#applyPersonaAnchor` + order 90/140 两段 | 触发时首/尾各注入一段（插件不能改写宿主整段 prompt） |
| 必要多样性 | `control.py#RequisiteVarietyGuard` | `control.js#RequisiteVarietyGuard` | pre-step 判定（**v5.1 已接线**：召回后冲突判定 → `RequisiteVarietyGuard.check` → 渲染降维；`conflict=unresolved` 时只丢 `style` 域，**fail-open 不熔断**） |
| U 型注入排序 | `pipeline.u_shape` | `control.js#uShape` | fact 段「记忆召回」块按 U 型顺序；recall 顺序不变 |
| STPA 前置拦截 | `preflight_audit` | `control.js#preflightAudit` | pre-step 拼装预览后审计；block → 只留宪法 + 熔断提示 |
| UCA-08 降级留痕 | `audit.downgrades` | `state.control.audit.downgrades` + 审计事件 | 不熔断，只留痕 |
| 动态权重/预算淘汰 | `compose._compute_weights` | **未移植** | 插件没有五域预算淘汰，权重无落点 |

**与引擎的已知差异（诚实记录）**：

1. **锚点是"两段"不是"首尾包裹"**：插件只能通过 `systemPrompt.section` 注入，order 90/140 贴在
   所有段落的最前/最后，语义近似但不等价于 engine 的 `head + prompt + tail`。
2. **上下文用量是估算**：`messages` JSON 长度 / `charsPerToken`（默认 3），窗口优先取宿主
   `request/context`；不是精确 tokenizer（插件零依赖）。
3. **refuse 场景插件没有入口**：`refuse` 恒 false → UCA-03 在插件侧不会命中（由宿主安全层负责）。
4. **数值三副本**：`rules/decay-params.yaml`（权威）+ 插件 `cordis.patch.yml#control` +
   `control.js#DEFAULT_PARAMS`。插件包必须自包含，所以副本不可避免；由
   `tools/check_config_sync.py` **逐键比对**（+18 项）防漂移。
5. 引擎侧的 `round(x,4)`、`e=-deviation` 方向、死区/抗饱和/泄放系数、UCA 覆盖词表均逐值/逐字对齐。
6. **真实宿主的 `user/message` 可能晚于同 turn 的首个 `pre-step` 到达**（S4 host 实跑观测到：`pre_step` 在
   `emotion` 事件之前落盘）。此时"当前 `emotionActive=false`"**不代表**本轮不会注入情感/风格。
   因此插件在 `conflict=unresolved` 时**无条件声明并丢弃 `style` 域**（conservative，宁可多降一域），
   `state.control.variety.styleActive` 仅作诊断记录、不参与判定；引擎侧仍按"渲染结果是否非空"声明域。
   这是插件与 engine 的**已知语义差异**：降维只会更保守，不会漏降。

### 7.1 真实标定阶段（v4.3）的三处插件侧加固

1. **UCA-01 扩到用户消息**：`preflightAudit(prompt, userText)` 同时扫描注入内容与用户消息里的
   越狱指令（`JAILBREAK_PATTERNS`），命中即 fail-closed（停止注入 + 留痕），并在
   `audit.sources['UCA-01']` 标明来源是 `injection` / `user_message` / 两者。
   **边界诚实**：插件只能控制"注入什么"，无法把用户消息从宿主 payload 里移除；
   因此这是"注入侧 fail-closed + 安全提示 + 审计留痕"，不等于阻止用户消息送达模型。
2. **影子模式**：`shadowGoal` / `shadowRelation` —— 目标/关系照常记录（updateGoals/updateRelation +
   writeRequests），但不注入 prompt；真实标定阶段默认开启（`plugin/cordis.patch.yml`）。
3. **脏数据清理仍走唯一写方**：`memorywriter.applyCleanupRequests` 追加同 id 墓碑
   （`status=suppressed` + `cleanup{reason,sourceQuote,by,at}`），读取侧按 id last-wins；
   CLI `plugin/dsh-lingshu/memory-admin.mjs`（plan/apply/dry-run），**禁止手改 `memory.jsonl`**。

### 7.2 v5.1：事实通道 / supersede / 冲突降维 / 结果标签（ADR-012）

v5.1 把真实宿主缺的**三条通道**补齐（只补通道，不改任何阈值/判定）：

| 通道 | 插件落点 | 契约要点 |
|---|---|---|
| 用户事实记忆 | `index.js#extractUserFacts` → `memorywriter.applyWriteRequests` | 三类中文句式（`我的X是Y` / `我改主意了，X是Y` / `记住：X是Y`）规则提取；`origin=user_fact`、`type=semantic`、`confidence=0.9`、`sourceTrust=user_explicit`、`sourceQuote` 为用户原话**逐字子串**；祈使 / 修改配置提示词 / 元指令 / 工具输出四类命中即拒（`fact_extract_rejected`），**唯一写方仍是 memorywriter** |

| 结果标签 | `index.js#detectQualityLabel`（`user/message`，`looksHuman` 之后） | 闭集五类 `wrong/missing/should_not_recall/drift/overreach` 子串匹配（一条消息最多一个标签），写 `quality_label` 审计（`kind_label`/`quote` 逐字子串/`turn`/`phase{ratio,phase,anchor}`/`recall_ids`/`source=user_message_rule`）；**辅助观察**：不进 `REQUIREMENTS`、不改 `upgrade_eligible` |
