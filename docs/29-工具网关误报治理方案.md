# 29 · 工具网关误报治理方案（提案稿）

> **状态**：**提案，未采纳，未改代码**（2026-10-29）
> **触发**：一次普通会话里，`pwsh` / `grep` / `glob` / `read` / `edit` 五类宿主工具**连续 7 次**被判 `block`，
> 触发项集中在 `T-UCA-09`（`schema_invalid`）与 `T-UCA-13`。开发任务无法推进。
> **上位文档**：[`24-工具网关UCA.md`](24-工具网关UCA.md)（v1.2 权威版）。

---

## 1. 结论

1. **这是一次已发生过、且未从根上修掉的复发。** docs/24 §10.5 记录：v1.1 在真实会话 244 次 `tool_gate` 里判了 241 次 block（98.8%），
   开发任务完全无法进行；v1.2 逐条修掉了**当时观测到的形态**（T-UCA-08 ×227、T-UCA-06 ×18、T-UCA-02 ×10、T-UCA-05 ×6、T-UCA-09 ×3）。
   本次复发说明 v1.2 修的是**样例**，不是**类别**：`REGISTRY` 里已经登记了宿主工具（`HOST_TOOL_SPECS`，含 `schema: {}`、`allowUnknown: true`），
   但真实调用仍然落进 `T-UCA-09`。
2. **当前形态的根因尚未确证。** 我只拿到三样证据：`T-UCA-09 → schema_invalid`（`tool-gateway.js:600`）、
   注册表对宿主工具显式写 `allowUnknown: true`（`tool-gateway.js:174-179`）、以及 `schemaInvalid(ctx)` 在真实事件上为真。
   这三条互相矛盾，说明**判定时拿到的 `ctx` 与 sim 里构造的 `ctx` 不是同一个形状**。在补齐取证之前不该改判定逻辑。
3. **建议的顺序是"先取证、再分级、最后才动默认值"。** 直接调 `defaults.unknown` 属于拿安全换安静，
   会同时削弱真正的拦截面（T-UCA-02/05/06 这次没有误报，不该被连累）。

## 2. 证据

| 事实 | 出处 |
|---|---|
| `T-UCA-09` = `schema_invalid` | `plugin/dsh-lingshu/tool-gateway.js:197` |
| 宿主工具已登记，且 `schema: {}, allowUnknown: true` | `tool-gateway.js:174-179` |
| `schema_invalid` 判定 = `schemaInvalid(ctx)` | `tool-gateway.js:600` |
| 参数键名需"已声明"否则判非法（历史注释） | `tool-gateway.js:112`、`:1185` |
| `tool-gateway-detective-sim.mjs:73` 已有一条"不误判 T-UCA-09"的用例 | 该文件 |
| v1.1 真实误报率 98.8%，v1.2 只修已观测形态 | docs/24 §9、§10.5 |

补充一个结构性事实：**DSH 目前只有 `tool/call` 与 `tool/result` 事件，没有 dispatch 前的钩子**（网关自己的强提示里写明）。
所以现在这套判定是**事后检测**——它拦不住已派发的调用，却照样写审计、照样打强提示。
后果很具体：判 block 的调用**照常执行成功**，于是"拦截"既不保护也不可信，只制造噪声。

## 3. 根因：**H3 已确证**（2026-10-29，`tool-gateway-forensics.mjs` + 真实 audit）

`gateToolResult()` 把宿主事件里的 `data.arguments`（**JSON 字符串**）原样塞进 `call.args`；
`tool-gateway.js:502` 的 `typeof args !== 'object'` 因此恒真，`schemaInvalid()` 对**每个带参数的工具调用**返回 true
→ 全量 `T-UCA-09` block。**规则语义没错，是入参形状错了。**

真实数据（`~/.dsh/plugins/dsh-lingshu/workspace_qq/audit.jsonl`，`policy_version=t-uca-1.2`）：

| 事实 | 数 |
|---|---|
| `tool_gate` 事件 | 395 |
| block | 393（**99.5%**） |
| 其中 T-UCA-09 | 389 |
| read / grep / glob / pwsh / edit / write | 各 **100%** block |
| `lingshu_status` | 2 allow + 2 block——**无参数那次 allow，带 `verbose` 那次 block** |

最后一行是判别式：同一工具、同一策略，**只随"有没有参数"变化**。这是"args 被当成非对象"的特征，
不是规则过宽。H1/H2/H4 由此排除（`enforceable=true` 说明条目存在、注册表没被覆盖；`allowUnknown` 分支根本走不到）。

**修复**：`index.js` 新增 `normalizeArgsForGateway()`——只在能解析成对象时收窄；解析失败/被截断/数组一律保持原样，
维持既有 fail-closed。`argsDigest` / `argsHead` 仍用**原文**，审计不可被"解析后"改写。
回归：`tool-gateway-sim.mjs` **85/85**、`persona-prompt-sim.mjs` PASS。`policy_version` **未升**——规则矩阵一字未改。

> 由此，本文档 §4 的 L0（拆分 reason code）**不是**修这个误报的必需项：规则没错，改默认值只会掩盖症状。
> L1 保留为发布门禁（这次正是它把 99.5% 翻出来的）。L0 降级为"待观察"，L2 仍是结构议题。

## 3.1 原始候选（保留作记录）

- **H1 · 事件形状不匹配**：宿主 `tool/call` 的真实载荷（args 可能被包一层，或工具名带前缀/命名空间）与 `HOST_TOOL_SPECS` 的键对不上，
  `registry[tool]` 取到 `null`，进而 `schemaInvalid` 以空 schema 判非法。
- **H2 · `allowUnknown` 未接线**：字段存在于注册表，但 `schemaInvalid` 的未知键分支没有读它（`:174-179` 与 `:177` 的语义可能只在声明侧）。
- **H3 · 判定输入不是 args 而是整个 call**：若 `ctx.args` 实际含 `id/tool` 等包装字段，空 schema 下必判非法。
- **H4 · 状态被宿主覆盖**：`state.tool_registry` 由外部注入（`:420-424`），若注入的是精简表，会覆盖 `REGISTRY`。

## 4. 方案（三层，L0 可当天做，L2 是结构性修复）

### L0 · 止血：给 `T-UCA-09` 分档，但不动真拦截面

把 `schema_invalid` 拆成两个正交 reason code：

| 新 code | 判据 | verdict |
|---|---|---|
| `schema_invalid`（保留） | 参数命中**控制字符 / 分隔符 / 同形字**（真注入迹象，docs/24 §3 T-UCA-09 原义） | `block` |
| `schema_unknown`（新增） | 仅"形状/未知键"不匹配，且工具在注册表内 | `allow_with_log` + `ucas` 记录 |

要点：**注入类迹象一条不放**，只把"我不认识这个参数"从 block 降级为 warn。
这条改动同时解决"拦不住却打 block"的荒谬状态——warn 本来就不承诺阻断，审计口径反而更诚实。

### L1 · 取证闭环：先量化，再谈修法

新增 `plugin/dsh-lingshu/tool-gateway-forensics.mjs`：

1. 读真实数据根的 `audit.jsonl`，筛 `kind=tool_gate`；
2. 按 `verdict × ucas × tool` 分桶，输出**误报率**（按工具被判 block 但调用在 `tool/result` 侧成功来判定）；
3. 打印 3 条命中样本的 `canon(args)` 前 200 字符（去敏：不含 `content/body` 正文）——这是定位 H1–H4 的唯一可靠途径；
4. 作为**发布门禁**：`docs/24 §9` 已经要求"已知误杀面必须与规则一起发布"，但一直是文档约定、不是机检门禁。
   建议落成硬门禁：单个工具 24h 误报率 > 1% 时，`tool-gateway-sim` 之外再跑 forensics，不达标不许发版。

### L2 · 结构：把"声明"从硬编码清单改为宿主上报

1. **注册表由宿主契约生成**：DSH 已有工具 schema（`tool/call` 事件里就带），网关应消费它，而不是维护 `HOST_TOOL_SPECS` 手工表；
2. **fail-closed 只对"有副作用"的工具生效**：`mutating`（write/edit/pwsh/…）→ 未知即 block；
   纯读（read/grep/glob/get）→ 未知即 `allow_with_log`。依据是 docs/24 §4 自己的原则"只读且无状态风险 → allow + 记录"，
   当前实现对只读工具没有兑现这条；
3. **判定对象固定为 args**：`ctx.args` 与 `ctx.call` 分开存，规则只读 `args`，避免 H3 这类形状污染；
4. **DSH 侧补 dispatch 钩子**（跨仓库）：没有前置钩子，这套矩阵在宿主里永远只能是"事后统计"。要么补钩子，
   要么在文档里把它的定位从"前置闸"改成"事后审计+告警"，别再声称 block。
