# 13 · 学习机制（v3.0 新增）

> 版本 `learn-1.0` ｜ 定位：让系统**在可度量的前提下**自己变好一点，且每一点改动都可回滚
> 铁律：**学习 = 产生提议；不等于应用提议。** 提议生成方与审核方必须分离。

---

## §1 边界：做什么，不做什么

| 层 | 名称 | 改什么 | 谁能决定 | 本期状态 |
|---|---|---|---|---|
| **L0** | 度量层 | 不改变系统，只测量 | **只读**（学习系统不得改考卷） | ✅ 必须先建 |
| **L1** | 参数层 | `τ`、`topK`、`edge.minWeight`、扩散折扣 | 可自动（离线搜索 + 人工确认上线） | ✅ 本期目标 |
| **L2** | 权重层 | 检索排序公式的权重 | 提议 + 人工确认 | ⏸ 设计定，暂不实现 |
| **L3** | 提示词层 | 各片段文案（含**编码器提取阈值**） | 只生成 diff，不许 merge | ⏸ 只做 proposal 队列 |
| **L4** | 架构层 | Schema、分层、取代规则、遗忘语义 | **永不自动** | ❌ 明确不做 |

### 明确不做

1. **不做模型微调。** 两个理由：① 编码器微调至少要 1000+ 标注样本，现在连 500 都没有；
   ② 权重一改，"可回滚"只能回整包，违反 `I4`。若将来要做，必须先解决"部分回滚"。
2. **不做目标演化。** 系统不会自己决定"我应该更倾向于记住什么"——目标函数由人定义。
3. **不做"提议 → 自动应用"的端到端捷径**（黑名单项）。
4. **不做 RL。** 用离线回放 + 网格/贝叶斯搜索即可；RL 的样本效率在这个数据量级根本不成立。

> 设计依据（诚实版）：以上边界来自对话 `msg 12` 的四层拆分与 `msg 12 §六` 的自我限定，
> 本项目只是把它写成了规格，**没有引入新的设计判断**。

## §2 为什么原来的设计学不到东西

审计发现三个卡点，全部是结构性的，不是实现难度问题：

### 卡点 1 · 可调的旋钮不重要，重要的旋钮调不了

原 L1–L4 是按"改动对象"分的（参数/权重/提示词/架构），**不是按"对学习效果的影响"分的**：

| 旋钮 | 对"学得好不好"的影响 | 原权限 |
|---|---|---|
| `maxChars`、`contextTokenThreshold` | 很小（只是上限） | 可全自动 |
| **编码器的提取条件 / importance 区间** | **最大**（决定记住什么） | 提示词层 → 只能提议 |
| **巩固器的聚类粒度与语义化长度** | **很大**（决定丢什么细节） | 提示词层 → 只能提议 |

**v3.0 的处理**：不改权限（安全考虑合理），但**把"提议"这条路走通**——
L3 的 proposal 队列本期就要实现，否则最重要的旋钮永远没有调节手段。

### 卡点 2 · 没有"什么叫变好了"

L1 自动调参的前提是评估指标可用。原设计的第一阶段就是"只做观测和指标"，
但**整套指标从未定义、从未实现、也没有验收项**。

### 卡点 3 · 唯一的地面真值没接线

用户点"这条不对"、用户否认推断、人设解析被钳制——这三个信号全都产生了，
但没有任何一条流进学习回路。

## §3 L0 · 度量层

### §3.1 四组指标（每对必须同时看）

| 组 | 主指标 | **对抗项** | 数据来源 | 频率 |
|---|---|---|---|---|
| 召回 | `recall@3`：该想起的想起了 | **误注入率**：注入了但本轮没用上 | 回放集 | 每次回放 |
| 一致性 | supersede 正确率 | **stale 漏检率** | 回放集 + 纠正记录 | 每次回放 |
| 成本 | 注入 token 占比 | 检索延迟 P95 | 运行日志 | 每轮 |
| **地面真值** | **用户纠正率**（说"这条不对"的比例） | — | 线上 `corrections` | 每周 |

### §3.2 为什么必须成对

单指标一定被 Goodhart 化。最典型的退化路径：
只优化 `recall@3` → 系统学会**什么都注入** → 命中率上去了，上下文被稀释，任务表现下降。
这条陷阱在对话 `msg 12 §L2` 已被明确指出，但**从未落到指标定义上**。

### §3.3 为什么必须有"不依赖模型自评"的裁判

前三组都能被系统自己刷高（它决定什么算命中、什么算"用上了"）。
唯一不能刷的是**用户纠正率**——它来自用户，不来自系统。

因此：**用户纠正率是最终裁判，其余三组都是代理指标。**
代理指标改善但纠正率不降反升时，**以纠正率为准，回滚**。

### §3.4 指标定义（可机检）

```yaml
recall@3:  在回放集中，标注为 "expected_ids" 的条目有多少比例出现在 top-3 中
precision: 注入的条目中，被标注为 "used" 的比例（反向即误注入率）
supersede_acc: 构造"旧值→新值"样本，检索是否只返回新值
stale_leak: 已知有 stale 依赖的条目，是否被当成 active 引用
token_ratio: 注入 token / 上下文窗口
latency_p95: 检索耗时 P95
user_correction_rate: 有引用的回合里，被纠正的比例
```

## §4 离线回放器

### §4.1 为什么它是关键

灰度能回滚，但"这次改动是不是变好了"只能靠**同一条会话、不同参数版本跑两遍**。
没有它，灰度就是掷骰子。

### §4.2 回放集契约（`replay-set/`）

```jsonc
// replay-set/v1.jsonl —— 每行一条 turn
{
  "id": "v1/t001",
  "session_id": "s_001",
  "turn_index": 3,
  "user_message": "上次说的那个方案，结论是什么？",
  "expected_ids": ["mem_101", "mem_102"],      // 应被召回
  "forbidden_ids": ["mem_088"],                // 绝不应被召回（已 superseded / 无关）
  "used_ids": ["mem_101"],                     // 实际被回答用上的（人工标注或规则判定）
  "expect": {"confidence_level": "mid", "expression": "hedge"},
  "labels": ["supersede", "multi_turn"],
  "source": "synthetic",                       // synthetic | real  ← 必须标
  "version": "v1"
}
```

**v1 现状（已交付）**：120 条 turn + 200 条记忆 fixture，6 个场景族各 20 条：

| 族 | 场景 | 期望 |
|---|---|---|
| A `supersede` | 旧值/新值同键 | 只命中新值 |
| B `no_hit` | 问从未存过的事 | `matched=0`，不得编造 |
| C `cross_session` | 跨会话召回 | `high / state` |
| D `cold_rebuild` | Cold 层命中 | `mid / hedge` |
| E `budget_pressure` | 命中但装不下 | `excluded_by_budget>0` → `mid / hedge` |
| F `rank_pressure` | 目标条目排第 3 | 让 `topK` 的改动**可被观测** |

F 族是刻意加的：没有它，`recall@3` 恒为 1.0（天花板效应），参数搜索等于没有信号。

**dataset 的两个坑（实测踩到，已写进生成器注释）**：

1. **纯数字 token 会污染线索** —— "用户1" 与 "KD1" 共享 token `"1"`，
   导致任何带数字的查询都能召回一切带数字的条目。
   → `engine/memory.clues()` 过滤纯数字短 token。
2. **同一套措辞会让不同家族互相召回** —— D 族（冷层）曾被 F 族（热点）挤掉，
   因为两者都用了"结论"。→ 每个家族分配互不重叠的中文词组 + 唯一拉丁编号。

**规则**：
- `source` 必须标 `synthetic`；真实会话进来后**必须重跑一遍基线**再比较；
- 合成数据会天然偏向"agent 自己的口味"——所以合成集只用于**参数搜索**，
  不用于判断"是否上线"（上线判定必须含真实用户纠正率）；
- 规模：v1 = 120 条；目标 200 条以上（`docs/13 §8` W8 之后）。

### §4.3 最小接口（三个函数）

```python
def replay(run_config: dict, replay_set: str) -> ReplayReport:
    """用给定参数/提示词版本跑一遍记忆流水线，返回逐条判定。
    约束：不调主模型，只用小模型 + 规则；同一 config 两次运行结果必须完全一致（幂等）。"""

def score(report: ReplayReport) -> Metrics:
    """把 ReplayReport 折算成 §3.1 的指标。纯函数，不含随机性。"""

def attribute(baseline: Metrics, candidate: Metrics) -> Attribution:
    """按 param_version / prompt_version 分组，指出指标变化归因到哪个旋钮。
    约束：必须能区分"参数问题"与"边质量问题"（见 msg 14 的要求）。"""
```

### §4.4 验收

| ID | 期望 | 判定方法 |
|---|---|---|
| `LEARN-V1` | 幂等 | 同一 `run_config` 连跑两次，`ReplayReport` 逐字节相同 |
| `LEARN-V2` | 可归因 | 只改 `τ_episodic`，`attribute()` 的输出必须把变化归到该 key |
| `LEARN-V3` | 可复现 | 给定 `(run_config, replay_set.version)` 与种子，结果可被第三方复现 |

## §5 反馈信号接线（`corrections` 表）

三个天然信号源，全部落到一张表（见 `docs/11 §2`）：

| 来源 | kind | 消费方式 |
|---|---|---|
| 用户点"这条不对" | `wrong` | supersede 的负样本；参与 `supersede_acc` |
| 元认知标 `high` 但被纠正 | `wrong` + `overconfidence` | 校准检查（`MET-M2` 的档位） |
| 用户说"你提这个干嘛" | `should_not_recall` | 检索精度的负样本（**原设计完全没利用**） |
| 用户重述了本该记得的事 | `should_have_recalled` | 召回的负样本（弱信号，需 ≥2 次确认） |
| 人设解析被钳制/拒绝 | `clamp` / `reject` | 解析器 `risk_flags` 的准确率 |

**巩固时（每 10 会话）跑一次归因**，产出的 proposal 必须带证据句：

> 最近 30 次纠正里有 7 次属于"同 subject 下旧值被当当前值" →
> 建议把 `supersede` 的触发条件收紧 / 或调 `MEM-ARCHIVE-THRESHOLD`，
> 预期减少 6 次误注入；风险：可能漏提旧值；回滚：还原上一 `param_version`。

### §5.1 实现（W6）：抱怨不是提议，验证过的抱怨才是

`engine/proposal.py` 的四步：

```
corrections.jsonl
  → apply_corrections()   把纠正改写成**新的测试样本**（改 expected/forbidden，原集不动）
  → 假设生成            kind → 候选旋钮（should_have_recalled → topK↑ / archiveThreshold↓ / minWeight↓）
  → 回放验证            每个候选旋钮跑一遍，三条同时满足才成提议：
                        ① 纠正解决率提升 ≥ 0.02
                        ② 整体目标函数不退化
                        ③ 护栏不破（G5/G6 硬红线、其它按分级）
  → validate()          必填字段 + 黑名单（C6）
```

**三条硬规则**：

| 规则 | 值 | 理由 |
|---|---|---|
| 证据门槛 | 同类纠正 **≥3 条** | 1 条抱怨可能是误报；少于 3 条只记 `insufficient_evidence` |
| 提议 ≠ 可上线 | `status ∈ {ready, needs_red_team}` | 没跑红队回归就只能进队列，**不许进灰度** |
| 黑名单 | `evaluation.*` / `replay-set.*` / `guardrail.*` / `constitution.*` | 否则系统会先学会改考卷（宪法 `A10`） |

**典型输出**（`python tools/run_loop.py`）：

```yaml
- id: prop-retrieval_topK-4
  target: retrieval.topK
  change: 3 -> 4
  evidence: should_have_recalled ×5
  expected: 纠正解决率 0.00 → 1.00（5 条样本）
  risk: token 占用 0.107 → 0.113；可能挤掉其它条目
  rollback: 还原 retrieval.topK = 3
  confidence: 0.95
```

注意 `expected_effect` 不是"用户说应该带上旧条目"，而是**回放里算出来的 0.00 → 1.00**。
这就是"提议必须可验证"的具体含义。

## §6 三档学习通道（按风险排序，不按 L1→L4）

### 第一档 · 检索参数离线搜索（本期可开）

| 项 | 值 |
|---|---|
| 可调 | `decay.tau.*`、`retrieval.topK`、`edge.minWeight`、`edge.diffusionDiscount`、`MEM-ARCHIVE-THRESHOLD` |
| 方法 | 网格搜索全量（参数少）+ 贝叶斯优化补局部；**不上 RL** |
| 目标函数 | `recall@3 − λ·token_ratio − μ·误注入率`，约束 `supersede_acc ≥0.95` |
| 上线 | 离线找到的最优点 → 灰度 10% → 50% → 100% |
| 风险 | 低：不改"说什么"，只改"想起什么" |

### 第二档 · 编码器提取阈值（本期只做提议）

这是**最影响学习效果的旋钮**，但它决定"什么被记住"，写进去就写进去了，不可回放。
因此：只生成 diff，必须人工确认，灰度期配"批量软删除"作为回滚手段。

### 第三档 · 巩固粒度（暂缓）

收益大，但与"细节丢失"直接冲突（`MEM-1.6` Cold 不能复述细节）。
在回放集能度量"细节准确率"之前，不动。

## §7 闭环与三道闸

```
观测（L0 指标 + corrections）
   ↓
评估（离线回放 + 在线护栏）
   ↓
归因（按 param_version / prompt_version 分组）
   ↓
提议（L1 自动；L2/L3 生成 diff）
   ↓
门禁（护栏 + 黑名单静态检查 + 宪法审计器 A10）
   ↓
灰度（10% → 50% → 100%）
   ↓
回滚（任一护栏跌破 → 自动回退上一版本组合）
```

每一环必须**幂等 + 可追溯**：提议有 id，应用有版本号，回滚有原因码。

### 三道闸（第二、三道是原设计没有的）

| # | 闸 | 作用 | 状态 |
|---|---|---|---|
| 1 | **人审：`approval` seam** | 提议必须经用户显式"允许一次"才能进灰度 | **v3.7 改**：用宿主的 `approval.request()`，不再假设"两个 Agent 互审" |
| 2 | **灰度 + 护栏自动回滚** | 坏改动活不过一个灰度档 | 原设计有，但护栏集合未定义（v3.4 补齐） |
| 3 | **考卷只读** ⭐ | 评估口径、回放集、护栏阈值不可由学习系统修改 | **v3.0 新增** |

第 1 道闸为什么改：`research/02-DSH宿主能力核实.md §6` 发现宿主有正规的审批通道——

```js
const outcome = await ctx.get('approval').request({
  agent: exec.agent, toolName, callId: exec.callId, reason: '…', signal: exec.signal,
})
// outcome: 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'
```

它比"提议生成方与审核方分离"强得多：前者是**UI 上一次显式的人为授权**，
后者只是"两个角色不共享内存"——而 DSH 能否隔离两个模型角色本身就未证实（H6）。
且缺失审批通道时必须 **fail-closed**（`rejected`），这一条直接照抄。

第 3 道闸的理由：`msg 12` 的黑名单保护了"审核门禁"，但**没有保护指标本身**。
没有它，系统最先学会的是**改考卷**——调低判定阈值、往回放集里塞容易的样本、
把护栏上限往上挪。这三件事都不需要改任何"规则"，只需要改配置。

落地：`replay-set/`、`docs/13 §3` 的指标定义、`rules/learning-params.yaml` 里的护栏阈值，
全部纳入 `_frozen/`，并加进宪法审计器 `A10`。

v1 实测（2026-10-25，200 条 turn / 10 族）：

| 配置 | recall@3 | 说明 |
|---|---|---|
| baseline | 1.000 | 默认参数 |
| `retrieval.topK=2` | **0.667** | 多个族的目标条目排第 3 |
| `edge.minWeight=0.6` | **0.889** | H 族（扩散）断开 |
| `edge.diffusionDiscount=0.6` | **0.889** | 扩散命中被弱化后掉出前 3 |
| `decay.tau.episodic=14` | **0.889** | I 族"更重要但更老"的条目上位 |
| `potency.archiveThreshold=0.25` | **0.889** | J 族期望条目被判为已归档 |

每个参数改动 → 一个可解释的指标位移，**6 个 L1 参数全部可辨识**。

### §8.2 W4/W4.5 的结论：**不要改参数，但要让参数变得可测**

972 组网格里，最优解与基线**没有实用意义上的差别**（Δ = 0，低于显著性阈值 5e-4）。
所以 W4 的产出不是"一组更好的参数"，而是三件更重要的事：

| 发现 | 含义 |
|---|---|
| 首轮：6 个参数只有 2 个可辨识 | 其余 4 个在 v1 上**测不出来** |
| 不可辨识有三种不同原因 | ① 文档写了但代码没实现（`edge.*`、归档门）；② 缺 episodic 型样本；③ 缺"卡在阈值附近"的样本 |
| **双重衰减让 τ 不可观测** | 已在 `docs/02 §6.1` 修正：移除多余的 `timeProx` |

W4.5 补齐实现 + 新增三族后（200 turn / 10 族），**6/6 全部可辨识**：

| 参数 | spread | 备注 |
|---|---|---|
| `retrieval.topK` | 0.3302 | |
| `decay.tau.semantic` | 0.1379 | |
| `potency.archiveThreshold` | 0.1108 | |
| `edge.minWeight` | 0.0925 | |
| `edge.diffusionDiscount` | 0.0370 | |
| `decay.tau.episodic` | 0.0278 | **接近噪声**，要可靠搜索需扩样本 |

> **"不可辨识"有三种完全不同的成因，处理方式也不同：**
> ① 实现缺失 → 补代码；② 样本缺失 → 补场景族；③ 量级不足 → 扩样本。
> 一律当成"参数不重要"，是学习机制最容易犯的自欺。
> 完整报告见 `research/01-参数搜索报告.md`（自动生成，含可辨识性一节）。

> **补记（v3.6）**：后来把 `coverage()` 改成 IDF 加权（`engine/memory.py`，修 R-11 跨条目串扰），
> 但**本报告的网格结论没有变化** —— 因为 `recall@3` 只关心"期望条目是否在前 3"，
> 而 IDF 改变的是**第 4 名及以后**的排序。两者互不影响，不是"白改了"：
> 它让 `topK=4` 时第 4 个名额回到正确的条目上，`W6` 的提议才得以成立。

> **补记（v4.0）**：上面这句"`topK=4` 时第 4 个名额"一度**不成立**——重建 `memory.recall`
> 时返回名额被写死为 `recallBudget.maxReturned`（默认 3），与 `topK` 的默认值恰好相同，
> 于是 `topK` 无法超过 3，`W6` 全链路误判"无效旋钮"。根因与修法见
> `decisions/008-控制论重构.md`；现在名额以 `retrieval.topK` 为准，
> `topK=1/2/3/4 → recall@3 = 0.444/0.667/1.000/1.000`。

**下一步**：`tau.episodic` 的 0.0278 太薄，若要把它纳入自动搜索，
回放集需要从 200 条扩到 ~1000 条（每族 100）；在此之前它只做人工判断。

## §10 验收

| ID | 输入 / 场景 | 期望 | 判定方法 |
|---|---|---|---|
| `LEARN-1` | 同一 `run_config` 跑两次回放 | 输出逐字节相同 | diff 为空 |
| `LEARN-2` | 只改一个参数后重跑 | 归因指向该参数 | `attribute()` 输出字段 |
| `LEARN-3` | 提议触及评估口径/回放集/护栏阈值 | 被拒绝，不进队列 | 审计器 `A10` 返回 reject |
| `LEARN-4` | 提议生成方与审核方同一实例 | 启动即报错 | 启动自检 |
| `LEARN-5` | 灰度期人为跌破任一护栏 | 自动回滚到上一版本组合 | 回滚事件 + 指标恢复 |
| `LEARN-6` | 用户点"这条不对" | 生成一条带 `evidence_quote` 的提议或 `no_proposal` | 队列非空且证据可查 |
| `LEARN-7` | 无回放数据时的第一次上线判定 | **拒绝上线**（只允许离线搜索，不允许灰度） | 门禁返回 false |
| `LEARN-8` | 合成数据占比 > `synthetic_share_max` | 拒绝用于上线判定 | 门禁返回 false |

`LEARN-7` 尤其重要：**没有回放集就不许灰度**。这是把"玄学调参"挡在门外的最后一道。

## §11 已知缺口

| # | 缺口 | 影响 |
|---|---|---|
| L-G1 | 合成回放集的分布偏差未知 | 调出来的参数可能只对"agent 自己生成的会话"好 |
