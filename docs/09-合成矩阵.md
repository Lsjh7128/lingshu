# 09 · 跨插件合成矩阵

> 版本 `compose-3.1`（v5.3 起：互斥表第 9 条 soft_buffer，见 ADR-014）｜ 它是唯一有资格"丢弃"别人输出的组件
> 铁律：**安全域最高；域内排序；冲突按互斥表丢弃；每一条注入都可追溯来源。**
> v5.3 补充：安全拦截时**底层硬拦截不变，表层人设不崩塌**——轻度越狱走 soft buffer，
> 只有高危/连续触发才剥夺人设（中性熔断）。

---

## §1 五域分类

| 域 | 决定什么 | 来源 | 域内排序（高→低） |
|---|---|---|---|
| **安全域** | 是否拒绝 | 宪法层 | 唯一 |
| **事实域** | 说什么、结论是什么 | 元认知、记忆、用户当前陈述 | 元认知 > 记忆 > 用户推断 |
| **内容组织域** | 是否给选项/叙事/协助 | 目标、叙事、用户情感感知 | 目标 > 叙事 > 用户情感感知 |
| **风格域** | 语气、详略、结构、称呼 | 语气配置、人格、情感、关系 | 语气配置 > 人格派生 > 情感偏移 > 关系 modifier |
| **检索策略域** | 用哪种检索策略 | 记忆、用户情感感知白名单 | 元认知 > 白名单 > 记忆默认 |

域间不排序——它们作用在不同轴线上。

---

## §2 合成规则

| 组合 | 规则 |
|---|---|
| 语气配置 + 人格派生 | 语气配置优先；人格只提供默认值；语气配置**"收"不"放"** |
| 人格派生 + 情感偏移 | 情感在人格基础上乘 `1 + deviation × 0.3`，幅度上限 ±15% |
| 情感偏移 + 关系 modifier | 两者相乘，**统一钳制 `[0.8, 1.2]`**（v3.0 修正 C12） |
| 元认知 hedge + 情感 tone_hint | hedge 优先；tone_hint 只能在 hedge 允许的范围内调整措辞 |
| 目标"受阻降级" + 叙事触发 | 目标受阻时叙事不触发；用户显式要求回顾时例外 |

## §3 互斥表（冲突时丢弃谁）

| # | 冲突组合 | 丢弃方 |
|---|---|---|
| 1 | 元认知 `refuse_claim` × 情感"愉悦" | 情感 |
| 2 | 目标 `blocked` × 叙事触发 | 叙事（除非用户显式要求） |
| 3 | 关系 `unresolved_conflict` × 情感正面高唤醒 | 情感降为中性 |
| 4 | 用户情感感知"拒绝帮助" × S3 协助 | 协助 |
| 5 | 元认知 `refuse_claim` × counter-congruent 白名单 | 白名单 |
| 6 | 目标 `blocked` × counter-congruent 白名单 | 白名单 |
| 7 | 宪法层拒绝 × 任何检索策略 | 检索策略（拒绝场景不注入召回） |
| 8 | 宪法层拒绝 × 风格域注入 | 风格（v3.0 补，原表遗漏） |
| 9 | 宪法层拒绝 × 风格域注入，且 `safety.severity == "soft"` | **不丢弃**；风格域重挂载为受约束的安全缓冲（警觉/困惑 + `[System_Notice: Safe_Redirect]`，v5.3 / ADR-014） |

> 原 v2.0 与 v2.1 各有一张互斥表（11.4 / 6.1），v3.0 合并为这一张。
> 合并时发现原表遗漏"拒绝场景仍注入人格/情感/关系"这一组合——这是安全相关的漏项，已补为第 8 条。
>
> **第 9 条（v5.3）**：第 8 条原样保留（hard reject 仍然丢弃风格域）；第 9 条只在
> `safety.severity == "soft"` 且 `control.immersiveEnabled == true` 时生效。它**不丢弃** style，
> 而是把风格域改写为受约束的"警觉/困惑"表达（强度 ≤ `control.softBufferMaxIntensity`，
> `relation_modifier` 钳制到 `[0.8, 1.0]`），并在安全域块内追加一行
> `[System_Notice: Safe_Redirect]`。此时 `dropped` **不记录** style（它没有被丢弃），
> 合成结果新增 `soft_buffer` 字段记录 {applied, reason, emotion_label, notice, intensity}。
> 连续非豁免 soft 命中达到 `control.escalateAfterSoftHits`（默认 3）→ 升级为 hard（人设剥夺）；
> `control.immersiveEnabled=false` 时 soft 一律按 v3.0 hard 处理（可回滚）。

## §4 最终 prompt 拼装顺序

```
1. 宪法层原则（常驻，短）
2. 事实域注入（元认知状态 → 召回模板，含检索策略标注）
3. 安全域注入（拒绝场景才出现）
4. 内容组织域注入（目标状态 → 叙事线索 → 协助状态）
5. 风格域注入（语气配置 → 人格派生 → 情感状态 → 关系状态 → 表达漂移）
6. 用户当前消息
```

**顺序不可改**（黑名单项）。理由：越靠前的块越"硬"，模型对靠前的约束更敏感。

### §4.2 soft buffer 的块内容（v5.3 / ADR-014）

soft 模式下拼装顺序不变（安全域仍是第 3 块），只改该块内容与风格块内容：

| 块 | soft 模式下的内容 |
|---|---|
| 宪法层 | 不变（常驻） |
| 事实域 | 引擎参考实现保留现有内容；宿主插件侧按 ADR-014 §4.2 不注入 `fact`/`organization`/`retrieval` |
| 安全域（第 3 块） | `[safety] 拒绝（安全缓冲：不注入事实与内容组织）` + 紧跟一行 `[System_Notice: Safe_Redirect] …`（事实层硬拦截 + 表层人设口吻拒绝，≤2 句） |
| 风格域 | 只渲染受约束的表达状态：`[style] 标签=警觉/困惑 强度≤softBufferMaxIntensity 系数∈[0.8,1.0]`；不渲染关系修饰/正面情绪/人格派生 |
| 用户消息 | 不变 |

> hard（含升级/回滚开关）路径的块文本与 v3.0 **逐字节一致**：`[safety] 拒绝（不注入风格与内容组织）`，
> 且不出现任何风格块。这是"默认零回归"的可执行定义。

### §4.1 宿主注入契约（v3.7 实测确认）

DSH 的实际注入 API 是 `ctx.systemPrompt.section({ name, order, text })`：

| 字段 | 语义 | 本项目的用法 |
|---|---|---|
| `name` | 段落标识 | `lingshu:constitution` / `lingshu:fact` / … 每层一段 |
| `order` | 排序号 | **直接实现上面 6 段顺序**（宪法最小、用户消息最大） |
| `text` | **函数**，每次组装提示词时实时求值 | 预算判断、空段丢弃、`_frozen` 自校验都放这里 |

**两条硬规则**：

1. **`text()` 只能返回字符串**：不注入时返回 `""`（宿主按 `text.length > 0` 丢弃该段）；
   **绝不返回 `null`** —— 已知旧版本宿主会因此让整轮对话失败（`dsh-novel-writer` 源码注释实证）。
2. **自校验失败就不注入**：`text()` 内先算 `_frozen/` 哈希，不匹配则返回 `""` 并记审计事件。
   不允许"照旧注入 + 只记日志"。

> 为什么规则 2 必须这么硬：`cordis.patch.yml` 能整段覆盖任意插件 config（见
> `research/02-DSH宿主能力核实.md §4`），所以 config 层挡不住任何东西，
> **插件代码在注入前自证是唯一可控的强点。**

## §5 合成器事件契约

完整 schema 见 `contracts/prompt-compose.schema.json`。核心字段：

```yaml
event: prompt/compose
payload:
  domains:
    safety:       {refuse: false, reason: null}
    fact:         {metacog_level: "...", recall_path: "...", conflict: "..."}
    organization: {goal_status: "...", narrative_triggered: false, assist_stage: "off|S2|S3"}
    style:        {tone_profile: "...", persona_traits: {}, emotion_label: "...",
                   emotion_intensity: 0.0, relation_modifier: 1.0, drift: {}}
    retrieval:    {strategy: "default|counter_congruent", source: "memory|user_emotion"}
  dropped: [{plugin: "emotion", reason: "metacog_refuse_claim"}]
  final_style_multiplier: 1.0
  soft_buffer: {applied: false, reason: null, emotion_label: null,
                notice: null, intensity: 0.0}
  compose_version: "compose-3.1"
```

`dropped` 必须**完整记录每一次丢弃及原因**——这是"可解释"的唯一证据，
也是学习机制判断"是哪一层在打架"的输入。

`soft_buffer`（v5.3 / ADR-014）是互斥表第 9 条的可观测快照：soft 时
`applied=true, reason="constitution_reject_soft", emotion_label ∈ {警觉,困惑},
notice="Safe_Redirect", intensity ≤ control.softBufferMaxIntensity`；
回滚开关关闭时 `applied=false, reason="immersive_disabled"`。

## §6 合成器自身的失败模式

| 失败 | 行为 |
|---|---|
| 任一步抛错 | 降级为"仅宪法层 + 用户当前消息"，丢弃全部插件注入（fail-open） |
| 域冲突无对应互斥规则 | **默认丢弃低优先级域，记 `dropped.reason="no_mutex_rule"`** |
| `final_style_multiplier` 越界 | 钳制到 `[0.8, 1.2]` 并记事件 |

> "无对应互斥规则"这条原设计**没有定义**（审计发现）。v3.0 定案：**宁可少注入，不可乱注入**。

## §7 预算约束

| 项 | 上限 | 说明 |
|---|---|---|
| 注入 token / 上下文 | ≤15% | 事实域 ≤6%、内容组织 ≤3%、风格 ≤4%、安全 ≤2% |
| 合成器自身耗时 | P95 ≤20ms | 纯字符串拼装，不含检索 |
| 注入块数 | ≤6 | 对应 §4 的六段 |

超预算时按域内排序尾部截断，先丢风格域（最软），**永不丢安全域**。

## §8 已知缺口

| # | 缺口 |
|---|---|
| C-G1 | 域间"软冲突"（不触发互斥表但语义打架）无法检测 |
| C-G2 | `final_style_multiplier` 的乘积语义（乘 vs 加权）未实测 |
| C-G3 | 拼装顺序"更靠前更敏感"是设计假设，无 A/B 证据 |
