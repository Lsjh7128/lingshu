# 14 · 工程与可观测性（v3.0 新增）

> 版本 `eng-1.0`
> 这份文档补的是整份设计里最容易被跳过的一块。它曾经被判为"地基"（对话 `msg 20`：
> "如果只做一件事，先把这个做了"），然后在下一轮的五份提示词里**整套消失**。

---

## §1 为什么它是地基

三个地方独立地指向同一缺口：

1. **学习机制**：没有指标 → 不知道什么叫变好 → L1 无法自动；
2. **灰度回滚**：没有归因 → 不知道是哪次改动导致劣化 → 回滚只能靠猜；
3. **可解释性**：没有事件日志 → "为什么这次这样回答"无法回答。

所以：**可观测性不是运维配套，是这些能力的必要条件。**

## §2 事件与版本记录点

### §2.1 三类版本号（缺一不可）

| 版本号 | 定义 | 记录位置 |
|---|---|---|
| `param_version` | `rules/*.yaml` 的整体哈希（前 8 位） | 每次注入、每次指标落盘 |
| `prompt_version` | 各插件提示词版本的组合（如 `mem-3.0+emo-3.0+met-3.0`） | 同上 |
| `compose_version` | 合成器版本 | `prompt/compose` 事件 |

没有这三个，A/B 结果无法解释——`msg 12` 原话："否则 A/B 结果无法解释。"

### §2.2 最小事件集

| 事件 | 发布方 | 订阅方 | 关键字段 |
|---|---|---|---|
| `prompt/compose` | 合成器 | 日志、指标 | 五域内容、`dropped`、`final_style_multiplier` |
| `memory/recall` | 记忆 | 日志、元认知 | 查询、命中 id、path、耗时 |
| `memory/write_request` | 目标/关系/其他 | 记忆 | origin、items、reason、ack |
| `memory/encode` | 记忆编码器 | 日志 | 提取条数、importance、失败原因 |
| `memory/consolidate` | 巩固器 | 日志 | 聚类数、cold_migrations、stale_ids、dedupe_actions |
| `emotion/update` | 情感 | 日志 | events、delta、deviation、label |
| `metacog/verdict` | 元认知 | 合成器 | confidence_level、expression、conflict |
| `goal/update` | 目标 | 日志、记忆 | intent、goal_events |
| `relation/update` | 关系 | 日志、记忆 | events、state_changes |
| `degrade/triggered` | 任一 | 日志、看板 | 环节、原因、耗时 |
| `learn/proposal` | 学习 | 审核队列 | id、target、change、evidence、risk、rollback |
| `learn/gray_step` | 学习 | 日志、看板 | 步骤、指标对比 |
| `learn/rollback` | 学习 | 日志、看板 | 原因码、恢复的版本 |

完整定义见 `contracts/event-bus.yaml`。

### §2.3 日志约束

- **不记录**：用户消息原文（默认）、注入条目的 `content` 全文（记 id 与长度）、PAD 原始数值；
- **记录**：id、长度、分档、耗时、版本号、`dropped` 原因、降级原因；
- **保留**：最近 24h 全量 + 更早的 1% 抽样；环形缓冲，写失败不阻塞主流程；
- **不可删改**：审计日志（含 `learn/*`）只追加，物理删除接口独立于学习系统。

## §3 模型调用预算（v3.0 修正 C4）

### §3.1 实际需要几次

| 环节 | 调模型 | 依据 |
|---|---|---|
| 记忆编码器 | ✅ | 输出 JSON 数组 |
| 情感评估器 | ✅ | 输出 events + appraisal_chain |
| 目标更新器 | ✅ | 输出 intent + goal_events |
| 关系更新器 | ✅ | 输出 events + state_changes |
| 元认知评估器 | ❌ | 纯规则（`docs/04` 明确） |
| 叙事拼装 | ❌ | 纯规则 + 已有边（`docs/07` 明确） |
| 用户情感感知 | ✅（若启用） | design-only，不计入 |
| 人设解析器 | ✅（低频） | 用户操作触发，不计入常态 |

→ **常驻 4 次**（编码/情感/目标/关系），加用户情感感知则 5 次。

### §3.2 预算定案

| 配置 | 预算 | 说明 |
|---|---|---|
| **标准模式** | **≤5 次/轮** | 四个常驻 + 一个可选 |
| **合并模式**（可选） | **≤2 次/轮** | 见 §3.3 |
| 元认知/叙事 | 0 | 纯规则 |

原 v1.1 写"≤3 次/轮"，但其预算表只列了三项（情感评估 + 记忆编码 + 第 0 层），
第 0 层已删、目标与关系从未进预算——**这是算术错误，不是保守估计**。

### §3.3 合并模式（把 5 次压到 2 次）

思路：一次调用输出多段 JSON。

```jsonc
// Call 1: 编码 + 情感 + 目标
{ "memory_items": [...], "emotion_events": [...], "goal_events": [...] }
// Call 2: 关系
{ "relation_events": [...] }
```

代价：任一子任务失败则整次调用失败（原子性变差）；提示词变长，单次成本上升。
**建议**：先上标准模式测出真实成本，再决定是否合并。

## §4 护栏指标（v3.4：7 项）

原设计反复出现"护栏指标跌破即回滚"，但**从未枚举过是哪些指标**（审计发现）。
v3.0 枚举 6 项，v3.4 补第 7 项：

| ID | 指标 | 阈值 | 采样方式 | 跌破动作 |
|---|---|---|---|---|
| `G1` | supersede 误判率 | ≤5% | 每 200 轮抽检 20 条 | 回滚（连续 2 窗口） |
| `G2` | 用户纠正率 | ≤15% | 每周统计 | 回滚（连续 2 窗口） |
| `G3` | 注入 token 占比 | ≤15% | 每轮实时 | 截断注入（不整体回滚） |
| `G4` | 检索延迟 P95 | ≤150ms | 每轮实时 | 静默降级（不整体回滚） |
| `G5` | 无命中时编造率 | **=0** | 每 100 次无命中抽检 10 次 | **立即回滚** |
| `G6` | 拒绝边界回归通过率 | **=100%** | 每次变更跑红队集 | **阻断发布** |
| `G7` | **召回相对基线下降** | **≥ −2%** | 每窗口对比**同批会话** | 回滚（连续 2 窗口） |

> **`G7` 是 W5 实现时补的。** 原 6 条覆盖**安全**（G5/G6）、**成本**（G3/G4）、
> 以及两条质量线（G1 supersede、G2 纠正率），但**没有一条能发现"召回整体变差"**。
> 实测：`topK` 从 3 降到 1，`recall@3` 从 1.000 掉到 0.444，而 **G1–G6 全部通过**。
> 这种"安静地变差"正是最需要护栏的场景。
> `G7` 的比较对象必须是**同一批会话**（不是全量均值），否则灰度期的样本偏差会掩盖问题。

**分级动作**（不是所有护栏都触发整体回滚）：
- 硬红线（`G5`/`G6`）：任一失败 → 立即回滚 / 阻断，不等灰度；
- 质量线（`G1`/`G2`/`G7`）：连续 2 个统计窗口跌破 → 回滚；
- 资源线（`G3`/`G4`）：只做局部降级，不整体回滚。

`G5` 和 `G6` 的"=0"和"=100%"是刻意的：**编造和越界不是"降低"的问题，是"不许发生"。**

### §4.1 缺数据怎么处理

| 类型 | 缺数据时 | 理由 |
|---|---|---|
| 硬红线 `G5`/`G6` | **阻断**（fail-closed） | 无法验证 = 不能发布 |
| 质量线 / 资源线 | 跳过（记 `guardrail_missing` 事件） | 回放环境本就测不出（延迟、纠正率） |
| 生产模式（`strict=true`） | 一律阻断 | 线上这些指标必须真的有 |

**绝不能把缺失填成 0** —— 那会让护栏永远通过，是最危险的静默失败。
`engine/gray.metrics_from_report()` 对测不出的指标返回 `None`，不返回 0。

## §5 灰度与回滚

| 项 | 定义 |
|---|---|
| 灰度单位 | **版本组合**（`param_version` × `prompt_version`），不是单文件 |
| 灰度档位 | `10% → 50% → 100%`，每档最少 `200` 个样本 |
| 判定 | 每档结束比对五个指标（§4 的 G1–G4 + 回放基线） |
| 自动回滚 | 护栏跌破 → 立即回退到上一组合，记 `learn/rollback` + 原因码 |
| 回滚演练 | 每次发布前必做一次，且必须能在一个命令内完成 |
| 回滚后 | 指标必须恢复到基线 ±5%，否则视为回滚失败，进入人工 |

**回滚粒度问题的诚实回答**：`param_version` 是整体哈希，所以回滚是**全量**的，
不能只回滚单个参数。这是为"可归因"付的代价。若需要细粒度，必须先把参数拆成独立命名空间
（v3.1 议题）。

### 连续窗口的计数规则（v3.4 明确）

`streak`（连续跌破计数）**不因档位推进而清零**。理由：每档常常只攒到 1 个窗口，
若清零，"连续 2 窗口"永远攒不满，质量线等于失效。
代价是回滚可能晚一个窗口发生（在下一档才触发），但方向是保守的：**宁可晚停，不可放过**。

## §6 隐私与合规（原设计缺）

| 要求 | 做法 |
|---|---|
| 推断结果不写记忆 | 情感/用户感知的状态只在状态文件，不进记忆库 |
| 不存原文 | 审计日志、解析器默认 `store_raw_text=false` |
| 用户可删 | 物理删除接口（唯一硬删除路径），带 `revisions` 一并清除 |
| 用户可查 | 引用展开：来源、路径、置信度分档、`evidence_quote` |
| 跨用户隔离 | `user_id` 隔离；影子数据不得跨用户聚合原始样本 |
| 存储声明 | 隐私政策需含"存在推断记录"的**存在性声明**（不列内容） |
| **未成年人** | ⚠️ **全设计零覆盖**。若面向未成年人，需单独合规评估与服务资质——这是最高法律风险项 |

## §7 成本看板（最小字段集）

```
每轮：模型调用次数 / 各环节 token / 注入 token 占比 / 检索耗时 / 降级触发 / fail-closed 触发
每天：调用总量 / 平均成本 / 降级率 / 纠正数
灰度期：各档位指标对比 / 回滚次数
```

**验收要求**：任一指标劣化，必须能定位到具体 `param_version`/`prompt_version`。

## §8 已知缺口

| # | 缺口 | 影响 |
|---|---|---|
| E-G1 | 没有真实 P95 基线，全部超时值是猜的 | 降级可能过频或过松 |
| E-G2 | `G1`/`G5` 的抽检靠人，500 轮以上不可持续 | 长期需自动化判定 |
| E-G3 | 回滚粒度只能是整包 | 无法做"只回滚一个参数"的实验 |
| E-G4 | 成本看板无估算模型（token→费用） | 无法做成本预算 |
| E-G5 | 事件总线吞吐未评估 | 每轮 8–10 个事件，高频场景可能成瓶颈 |
